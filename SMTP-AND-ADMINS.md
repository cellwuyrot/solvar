# SMTP и несколько администраторов

## Статус

Серверный код проверен на отдельной временной базе и локальном SMTP-моке.
Реальная авторизация в Trioz, TLS-соединение с ним и доставка во входящие НЕ проверены.
Публичный адрес https://smtp.trioz.ru/ открывает панель входа и не раскрывает параметры SMTP.
Нельзя считать адрес панели автоматически адресом SMTP-сервера.
Экран установки пароля подключён; его работа проверена браузером по HTTPS на локальном изолированном стенде. Это не подтверждение готовности внешнего SMTP или production-инфраструктуры.

## Настройка сервера

В личном кабинете Trioz получите точные SMTP host, порт, логин, пароль и разрешённый адрес отправителя.
Сохраните их только в серверном `.env` (никаких `VITE_SMTP_*`). Пример структуры, НЕ готовые реквизиты:

```dotenv
SMTP_HOST=
SMTP_PORT=465
SMTP_SECURE=true
SMTP_USER=
SMTP_PASSWORD=
SMTP_FROM=
SMTP_ALLOW_INSECURE_LOCAL=false
```

- `SMTP_HOST`: только имя сервера, без `https://`, пути или порта.
- Порт 465 обычно использует TLS с начала соединения (`SMTP_SECURE=true`).
- Если провайдер выдаёт 587/STARTTLS, используйте `SMTP_SECURE=false`; STARTTLS обязателен вне явно разрешённого локального мока.
- `SMTP_FROM`: один подтверждённый адрес, например реальный служебный ящик владельца, а не выдуманный адрес из примера.
- Проверка сертификата не отключается. Защита запрещает чтение файлов/URL из сообщения.
- Настройте SPF/DKIM/DMARC по инструкциям провайдера. Приём SMTP не доказывает доставку и не гарантирует отсутствие спам-фильтрации.
- Пароль и содержимое писем не выводятся в обычные журналы. Не помещайте `.env` в архив или систему контроля версий.

Сначала используйте staging, отдельную БД и тестовые адреса с разрешения их владельцев.
Тесты из админки разрешены только при `DEPLOYMENT_ENV=staging`; это не переключатель торговли.
Сервис не открывает произвольную публичную отправку писем и не активирует уведомления по торговым заказам.

## Права

- `owner`: владелец; может создавать/отключать администраторов и отправлять приглашения. Нужен повторный ввод собственного пароля, максимум 5 попыток за 15 минут.
- `admin`: работает с существующими административными данными; не управляет доступом команды и не меняет серверные секреты.
- Учётная запись без активного членства не получает доступ к управлению, даже если может пройти обычную авторизацию.
- Владелец не может отключить сам себя. Отключение сотрудника удаляет сессии; членство проверяется на каждом RPC-запросе.
- Создаваемый пароль — случайный серверный секрет, он не показывается владельцу и не рассылается. Сотрудник получает одноразовую ссылку и самостоятельно задаёт пароль 12–128 символов.
- Ссылка действует час, повторное использование отклоняется. После смены пароля старые сессии отзываются.
- Ошибка SMTP не удаляет учётную запись. Приглашение можно повторить; состояние «принято» относится только к SMTP-серверу.
- Назначать других владельцев через API нельзя. Bootstrap-владелец сохраняется при повторной миграции.

## Новая локальная база на Windows (PowerShell)

Не использовать рабочую базу. Команды запускаются из корня распакованного проекта:

```powershell
npm.cmd ci
npm.cmd run env:local
notepad.exe .env
```

В новом `.env` заполните собственные локальные `ADMIN_EMAIL` и `ADMIN_PASSWORD` (от 12 символов), оставьте сгенерированный секрет,
`NODE_ENV=development`, `WEBSITE_URL=http://localhost:4200`, `DATABASE_URL=file:./local.db`, `NOTIFICATION_WORKER_ENABLED=false`.
Не добавляйте боевые SMTP/Telegram-доступы в тестовое окружение. Сохраните и закройте редактор.

```powershell
npm.cmd run db:push --workspace=@template/web
npm.cmd run db:seed
npm.cmd run test:technical
npm.cmd run test:hardening
npm.cmd run typecheck
npm.cmd run build --workspace=@template/web
npm.cmd run dev:web
```

`db:push` здесь предназначен ТОЛЬКО для новой локальной базы. Windows в среде разработки недоступна; команды и path.win32 проверены, нативный запуск Windows ещё нужен.
Bun устанавливается через `npm ci`; не используйте `--ignore-scripts`. `npm.cmd` не требует менять ExecutionPolicy.

## Существующая база

Перед обновлением остановите запись в приложение, сохраните старый релиз и серверное окружение, сделайте snapshot и проверьте восстановление на отдельном пути.
Не запускайте seed, замену каталога или `db:push` на рабочей базе. Не удаляйте WAL-файлы.

```powershell
npm.cmd run db:backup
```

Команда выдаст путь нового snapshot; рядом создастся manifest с SHA-256. Замените пути ниже фактическими:

```powershell
$env:RESTORE_SOURCE = 'C:\Backups\solvar-actual-snapshot.db'
$env:RESTORE_DESTINATION = 'C:\Staging\solvar-restore-check.db'
npm.cmd run db:restore
```

Назначение ДОЛЖНО быть новым файлом: существующая база никогда не перезаписывается. Проверяются hash, размер, PRAGMA quick_check, копирование и повторная проверка.
Затем проведите прикладную smoke-проверку восстановленной базы в отдельном окружении.

После подтверждённого резервирования:

```powershell
npm.cmd run db:orders
npm.cmd run db:admins
```

Обе миграции сохраняют прежние записи. Перед изменением локальной SQLite автоматически создаётся отдельный проверенный snapshot.
`db:admins` назначит существующего пользователя из `ADMIN_EMAIL` владельцем только если владельца ещё нет.
Для удалённой libSQL нужны snapshot и проверяемое восстановление средствами провайдера; `REMOTE_BACKUP_REFERENCE` — ссылка/идентификатор этой операции, не автоматическая проверка удалённого backup.
Для обновления production используйте DEPLOYMENT-RUNBOOK.md после staging-проверки и подтверждения реального восстановления резервной копии.

## Восстановление и персональные данные

Снимки включают учётные записи и обращения. POSIX-права файлов 0600 не заменяют NTFS ACL в Windows.
Ограничьте доступ владельцем сервиса, шифруйте внешние копии, определите срок хранения и проверяйте восстановление регулярно.
Не переключайте production на восстановленную БД без проверки и остановки записи. Rollback кода не означает rollback данных; не теряйте новые обращения при откате.
