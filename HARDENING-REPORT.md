# SOLVAR — итог технического аудита и локального усиления

## Итог и границы

Работа выполнена на существующем коде, без замены архитектуры. Добавлены серверные ограничения, общий безопасный SMTP-транспорт и несколько администраторов с личными паролями. Рабочая база и production-инфраструктура не использовались и не изменялись. Это не сертификация безопасности и не подтверждение готовности всего monorepo к production.

Публичный сайт оставлен в информационном режиме. Торговые заказы, резервирование, подтверждение, реквизиты и уведомления по ним не активированы, даже «без оплаты». Включение административным чекбоксом, env или прямым RPC блокируется. Исторические записи/очереди сохранены без отправки. Контактные сведения и privacy берутся только из данных владельца; новая публичная форма обращений не добавлялась.

Исходные информационные/маркетинговые тексты не переписаны. Публичная композиция ограничена контактной страницей и privacy; прежние торговые страницы, компоненты корзины, карточек и главной сохранены в исходниках, но не смонтированы. Никаких вымышленных товаров/цен/реквизитов не добавлено. Исходный catalog-seed.json содержит четыре скрытых шаблона.

### Почему торговый сценарий не включён

В указанной для проекта России ч.3 ст.19 15-ФЗ запрещает дистанционную розничную продажу табачной продукции; ч.4–5 регулируют демонстрацию/информацию в торговом объекте, а не дают разрешение на интернет-витрину. [^https://www.consultant.ru/document/cons_doc_LAW_142515/fa5bef43e6be9f36d6364b63f3d473e5218db6ae]
Реклама табачной/никотинсодержащей продукции и перечисленных принадлежностей запрещена п.8 ст.7 38-ФЗ. [^https://www.consultant.ru/document/cons_doc_LAW_58968/3bfc26317bd01efad6f67aadf9981b248a57ef4b/]
Это технический безопасный выбор, не юридическое заключение. Одного согласия владельца или подтверждения 18+ в браузере недостаточно для включения неподтверждённой модели.

## SMTP и несколько администраторов

- Используется существующая почтовая инфраструктура Nodemailer, общий транспорт mail.ts, без второй торговой очереди.
- Поддерживаются implicit TLS и обязательный STARTTLS, проверка сертификата, лимиты времени, одиночные адреса, защита от CRLF/чтения файлов и URL-вложений. Небезопасный loopback разрешён только явно вне production для теста.
- https://smtp.trioz.ru/ открылся как панель входа, а не документация SMTP. Host/port/login/verified sender не угаданы. Пользователь должен взять параметры в панели провайдера.
- Владелец подтверждает личный пароль для операций с командой; лимит попыток и журнал событий. До 50 учётных записей; создать другого owner через API нельзя.
- Сотрудник получает одноразовую часовую ссылку и сам задаёт пароль 12–128 символов. Пароль не возвращается владельцу. Ссылки/тела писем/секреты не пишутся в обычные журналы приложения.
- При отсутствии/отказе SMTP учётная запись сохраняется, статус честный; доступен повтор приглашения. Отключение удаляет сессии и проверяется каждым RPC. Обычный admin не управляет командой и интеграционными пробами.
- Проверена служебная почта приглашений/сброса. Клиентские уведомления торговых заказов не включались. Реальные Trioz/Telegram/CAPTCHA не проверены без отдельного staging и доступов.

## Что сохранено

React/Bun/Hono/oRPC/BetterAuth/Drizzle и структура monorepo; прежние компоненты/страницы и данные; черновики каталога и управление лого; архивные заявки/история/внутренние заметки; старый механизм сохранения и очереди уведомлений (поставлен на паузу); статусы без новой CRM; исходные тексты и четыре скрытых seed-шаблона; lock-файлы зависимостей. Публичный API не отдаёт внутренние заметки и историю. Изменение политики не даёт разрешения на будущий запуск legacy-сценария без отдельного аудита.

## Зависимости

Снимки npm audit включены в qa-hardening. Версии не обновлялись массово, audit fix --force не выполнялся. Сравнивать отчёты нужно с одинаковыми workspace/omit-флагами.

| Область | Результат npm audit |
|---|---|
| web production: --omit=dev --workspace=@template/web | 0 |
| web включая dev | 4 moderate: esbuild / @esbuild-kit/core-utils / esm-loader / drizzle-kit |
| monorepo production | 46: 16 moderate, 30 high, 0 critical |
| monorepo всё | 63: 23 moderate, 39 high, 1 critical |

Критическое tar 6.2.1 приходит через desktop electron-builder 24.13.3/app-builder-lib (dev/build-инструментарий), не production web. Expo использует другую ветку tar. Принудительная подмена tar6→7/обновление всех Electron/Expo без нативных тестов не выполнялось. Root PM2 и прочие monorepo high остаются; поэтому не рекомендован исторический root npm start для новой production-поставки. Вспомогательный isolated-web-runtime audit=0 получен свежим разрешением web-зависимостей и не подменяет проверку поставляемого lock-файла.

## Производительность и визуальная проверка

Production-бандл собран и измерен в Chromium: точные файлы/байты и результат одного холодного запуска — qa-hardening/mobile-emulation-metrics.json; детализация чанков — build.log. В метрике учтены ВСЕ загруженные JS, включая modulepreload, а не только entry script.
Финальный прогон: LCP 2816 ms, DOMContentLoaded 2470 ms, загруженный JS 303573 байта (encodedBodySize). Это эмуляция 390×844, CPU×4, задержка 150ms, 1.6Mbps; не настоящее мобильное устройство и не статистика Core Web Vitals. Auth/react preload остаются в начальной загрузке, legacy/admin модули вынесены в lazy-ветки; tree-shaking-настройка исходного проекта сохранена. Эксперимент с onlyExplicitManualChunks не дал подтверждённой пользы и не включён. Улучшение скорости относительно исходного проекта не заявляется.
Скриншоты desktop/mobile включены; страницы информационного режима и администраторов проверены визуально, горизонтального overflow на 390px нет. Маркетинговый редизайн табачной витрины в этой безопасной поставке не выполнялся.

## Что требуется от владельца до запуска

1. Решение юриста/владельца о допустимой модели, достоверные контакты/реквизиты/privacy/сроки хранения. Не включать торговлю технической правкой константы без нового аудита.
2. Staging-доступы Trioz, SMTP host/port/TLS/verified from, SPF/DKIM/DMARC, контролируемые получатели; проверить реальные приглашения, отказ и попадание во входящие. Telegram/CAPTCHA отдельно, если потребуется допустимым сценарием.
3. Производственные домен/TLS/proxy/права, мониторинг, периодические шифрованные off-site backup и проверяемое восстановление; контроль журналов CDN/proxy, чтобы токены не записывались.
4. Нативное тестирование Windows/desktop/mobile и план совместимого устранения оставшихся monorepo advisories. MFA здесь не добавлена.
5. Отдельное проектирование разрешённого клиентского обращения/назначения ответственного/ответа, если нужна публичная форма. Полная CRM и новый workflow не внедрялись; существующий архив сохранён.

Точные команды: WINDOWS-START.md, DEPLOYMENT-RUNBOOK.md. Исторические TECHNICAL-FIXES.md / UPDATES-V2.md / TEST-RESULTS-V2.md и другие старые журналы помечены как исторические: их PASS и способы включения торговли не являются результатом этой поставки.
