# SOLVAR — безопасное обновление и эксплуатация

Это инструкция оператору, а не выполненное развёртывание. Production-инфраструктура не изменялась.
Windows: WINDOWS-START.md. Настройка почты: SMTP-AND-ADMINS.md. Ограничения: HARDENING-REPORT.md.
Торговый сценарий заблокирован константой в коде; переменные окружения и админка его не включают.

## Предварительные условия

- Node.js 24, npm и Bun 1.3.14; после `npm ci` Bun доступен скриптам npm.
- Отдельное staging-окружение, отдельные БД, SMTP-пользователь и получатели. Не копируйте рабочие секреты в тесты.
- Перед обновлением сохраните старый код, `.env`, базу и manifest в защищённом месте вне каталога релиза. Не публикуйте их через web root.
- Оператор должен знать фактический DATABASE_URL. Для локального SQLite в production нужен абсолютный постоянный путь, например `file:/var/lib/solvar/store.db`, не внутри сменяемого релиза.
- WEBSITE_URL — реальный HTTPS origin без пути; BETTER_AUTH_SECRET — стабильный случайный секрет 32+ символов; ADMIN_EMAIL — email существующего владельца. Не меняйте секреты при каждом рестарте.
- NODE_ENV=production, HOST=127.0.0.1, PORT=4200, BACKUP_DIR=/var/backups/solvar, NOTIFICATION_WORKER_ENABLED=false, SMTP_ALLOW_INSECURE_LOCAL=false. Адреса/пути — примеры, оператор обязан сверить их.
- TRUSTED_PROXY_IPS содержит только фактические адреса доверенного reverse proxy. Не доверяйте заголовкам произвольных клиентов.

## 1. Сборка новой копии отдельно от работающего релиза

Из корня распакованной новой копии:

```sh
npm ci
npm run test:technical
npm run test:hardening
npm run typecheck
npm run build --workspace=@template/web
npm audit --omit=dev --workspace=@template/web
```

Не запускайте общий `npm start`: он использует сохранённый исторический PM2-сценарий. Для нового web-развёртывания используйте Bun/systemd, после проверки соответствующего шаблона. Замечания root/desktop/mobile зависимостей не устранены.

## 2. Существующая база: backup и проверка восстановления

Остановите процесс приложения/запись в окно обслуживания. Дальнейшие команды выполняются из корня новой копии с отдельно установленным защищённым `.env`, указывающим именно проверенную базу. Не выполняйте `db:push`, seed или `db:migrate:solvar` на существующей базе.

```sh
npm run db:backup
```

Скрипт выводит фактический путь snapshot; сохраните рядом `.manifest.json`. Подставьте этот путь и НОВЫЙ целевой файл:

```sh
RESTORE_SOURCE=/var/backups/solvar/ACTUAL-SNAPSHOT.db \
RESTORE_DESTINATION=/var/lib/solvar/restore-check-UNIQUE.db \
npm run db:restore
```

Не используйте буквальные ACTUAL/UNIQUE: замените фактическими именами. Команда откажется перезаписывать существующий файл. Проверяются SHA-256, размер и SQLite quick_check. Дополнительно запустите staging с восстановленной копией и отдельным `.env`; убедитесь в наличии своих настроек/черновиков/истории. Это обязательный операторский smoke-test, не заменяемый quick_check.

```sh
npm run db:orders
npm run db:admins
```

Обе миграции создают дополнительную резервную копию до изменения локальной базы. Они аддитивны: сохраняют старые строки/пароли/каталог. `db:admins` назначает первого owner только существующему ADMIN_EMAIL, если owner ещё нет. При ошибке остановитесь; не исправляйте её удалением базы или повторным seed.
Для удалённой libSQL-базы нужен проверенный backup провайдера и REMOTE_BACKUP_REFERENCE. Скрипт не умеет самостоятельно удостоверять восстановимость удалённого backup. Сначала выполните отдельный restore-тест у провайдера.

## 3. Запуск и проверка

```sh
npm run serve:web
```

В другом терминале (если порт соответствует .env):

```sh
curl --fail http://127.0.0.1:4200/api/health
curl --fail http://127.0.0.1:4200/api/ready
```

Проверьте также реальный HTTPS-адрес, вход владельца, отсутствие каталога/корзины публично, раздел сотрудников, сохранение лого, отсутствие служебных полей в публичном API. `/health` — процесс жив, `/ready` — схема/настройки/владелец готовы. Ни один endpoint не доказывает доступность SMTP или качество резервной копии.

Шаблон deploy/solvar.service предполагает пользователя solvar, код `/srv/solvar`, Bun `/usr/local/bin/bun`, данные `/var/lib/solvar`, backup `/var/backups/solvar`. Перед установкой оператор должен адаптировать пути/права. Сервис пишет только в разрешённые постоянные каталоги. Не копируйте unit поверх действующего без проверки.
После установки адаптированного unit администратором сервера:

```sh
sudo systemctl daemon-reload
sudo systemctl restart solvar
sudo systemctl status solvar --no-pager
sudo journalctl -u solvar -n 80 --no-pager
```

## 4. Reverse proxy / секреты / контроль

TLS-сертификат и HTTPS настраивает оператор. В deploy/nginx-solvar.conf есть базовый пример, не универсальная production-конфигурация. Сохраните действующую TLS-конфигурацию, проверьте `sudo nginx -t` перед reload. Закройте внешний доступ к Bun-порту. Передавайте Host корректно, не кэшируйте `/api/*`, ограничьте размер тела запроса. Не журналируйте URL токенов сброса пароля, request/response bodies, Authorization/Cookie или SMTP-пароли. Учтите также CDN/балансировщик и их журналы. HTTPS и фактические настройки прокси в этой работе не проверялись.

Проверяйте 5xx/readiness, ошибки служебной почты, заблокированные аккаунты, свободное место и возраст backup. Очередь исторических торговых уведомлений остановлена намеренно; не включайте её ради устранения «зависших» записей. Зафиксируйте бизнес-решение/правовую модель отдельно.
Ротация backup, внешнее шифрованное хранение, retention и мониторинг — обязанности оператора; автоматическая off-site-система здесь не подключалась.

## 5. Откат

Сначала остановите приложение. Не откатывайтесь на старый небезопасный публичный торговый сценарий. Snapshot восстанавливается только в новый файл, затем проверяется отдельно. Для переключения укажите новый проверенный абсолютный DATABASE_URL в защищённом `.env`; исходный файл и snapshot не удаляйте. Учтите потерю изменений после момента backup; решение о таком откате принимает владелец. Миграции не имеют автоматического destructive down-скрипта.

## 6. Проверка реального SMTP только на staging

Возьмите host/port/TLS/login/пароль/подтверждённый from в панели Trioz. Её URL не является подтверждённым SMTP-хостом. Настройте SPF/DKIM/DMARC по данным провайдера. Создайте тестового сотрудника с контролируемым email, проверьте приглашение во входящих/спаме, одноразовость ссылки, истечение срока, отключение доступа и сценарий отказа SMTP. Зафиксируйте provider ID/время без токена и персональных данных. Ответ accepted означает только приём провайдером, а не доставку. Эти реальные действия в поставке НЕ выполнялись.
