# SOLVAR v2 — заявки, Telegram/почта, счета и антиспам

## Сценарий
Покупатель отправляет заявку без оплаты. Продавец подтверждает наличие и доставку, получает счёт/ссылку в своём банке или платёжном провайдере, сохраняет номер, согласованную сумму и ссылку в админке, затем копирует сообщение для ручной отправки покупателю. Статус «Оплачено» — ручная отметка после банковской сверки. Автоматическое создание банковского счёта, проверка оплаты по webhook и фискализация не реализованы: банк/провайдер и статус продавца не предоставлены.

## Новое в админке
«Заявки / Telegram»:
- внутренние заметки до 5000 символов, сохранение в базе, защита от перезаписи из другой вкладки;
- номер счёта, согласованная сумма, HTTPS-ссылка разрешённого банка, статус оплаты, копирование сообщения;
- поиск по имени/телефону/ID, фильтр статуса, страницы по 50 заявок;
- история создания и административных изменений без текста заметок;
- независимые Telegram/SMTP уведомления, состояния, попытки, ручной повтор и тест каждого канала;
- удаление данных завершённой/отменённой заявки с подтверждением. Telegram, почтовые ящики и бэкапы очищаются отдельно.

Заметки не возвращаются публичному API, не включаются в уведомления продавцу и не отправляются клиенту.

## Перед установкой
1. Отзовите токен, ранее опубликованный в переписке. Новый храните только на сервере.
2. Заполните настоящие реквизиты, контакты, оферту, оплату, доставку и политику обработки данных; проверьте требования к ККТ и передаче данных через Telegram/почту. Счёт или СБП не являются автоматическим освобождением от ККТ.
3. Сделайте резервную копию действующей БД и проверьте восстановление. Рабочий `.env` и базу не заменяйте файлами из примеров.
4. Сначала разверните staging на копии данных. Архив не меняет сайт solvar.ru сам по себе.

## Миграция существующей базы
В среде сборки:
```sh
npm ci
npm run db:orders
npm run build:web
```
`db:orders` создаёт недостающие таблицы и добавляет колонки к старой `shop_orders`, не удаляя и не перезаписывая товары, auth или JSON заявок. Повторный запуск допустим. Для ранее открытых заявок создаются блокировки нормализованных телефонов. Если в старой базе уже несколько активных заявок с одного телефона, разберите их вручную; миграция не удаляет исторические дубли.

Не используйте `db:push` для автоматического обновления рабочей БД. Для новой пустой установки нужны исходные `db:push`, `db:seed`, затем `db:orders`. Пароль администратора seed не меняет, если пользователь уже существует.

`ORDER_GUARD_SECRET` или используемый вместо него `BETTER_AUTH_SECRET` должен быть постоянным и не короче 32 символов. Если меняете этот ключ, повторите `db:orders` для восстановления блокировок телефонов; существующие browser-cookie станут недействительны и перевыпустятся.

## Production без мобильных/desktop/tooling-зависимостей
Соберите в CI/staging, перенесите исходники web и `packages/web/dist`. В отдельной чистой production-копии:
```sh
npm ci --omit=dev --workspace=@template/web --include-workspace-root=false
```
Для исполнения нужен отдельно установленный Bun 1.3.14. В этой установке root-пакеты Bun/PM2 не устанавливаются автоматически. Используйте системный Bun и `deploy/solvar.service`, адаптировав пути, пользователя и права. Не запускайте `vite dev` на публичном сервере. `deploy/nginx-solvar.conf` — шаблон для слияния с текущей TLS-конфигурацией; он не применён к вашему хостингу.

Если используется managed Runable, согласуйте изменения шаблонных серверных файлов (`__server.ts`, `api/__core/app.ts`, `database/__client.ts`, hono-dev-plugin) с возможностями публикации площадки. Локальная проверка обычного Bun/npm-сервера не доказывает прохождение её protected-files pipeline; реестр `.runable` не подменялся.

## Обязательные настройки сервера
```dotenv
NODE_ENV=production
WEBSITE_URL=https://solvar.ru
HOST=127.0.0.1
PORT=4200
# Пример для Nginx на том же сервере, который ПЕРЕЗАПИСЫВАЕТ X-Real-IP:
TRUSTED_PROXY_IPS=127.0.0.1,::1
# Локальная БД — постоянный диск, не публичная папка сайта:
DATABASE_URL=file:/var/lib/solvar/shop.db
BACKUP_DIR=/var/backups/solvar
ORDER_CAPTCHA_REQUIRED=true
TURNSTILE_SITE_KEY=
TURNSTILE_SECRET_KEY=
NOTIFICATION_WORKER_ENABLED=true
TELEGRAM_BOT_TOKEN=
SMTP_HOST=
SMTP_PORT=465
SMTP_SECURE=true
SMTP_USER=
SMTP_PASSWORD=
SMTP_FROM=
PAYMENT_ALLOWED_HOSTS=
```
Секреты заполните на сервере; не присылайте в обычный чат. Используйте отдельный SMTP-пароль/учётную запись, SPF/DKIM/DMARC своего почтового домена. TLS-сертификат SMTP проверяется; для порта 587 задайте `SMTP_SECURE=false` — STARTTLS остаётся обязательным. Небезопасный локальный SMTP разрешён только в тестовом режиме, не в production.

`PAYMENT_ALLOWED_HOSTS` — точные домены фактического банка/провайдера через запятую, без схемы, пути или wildcard. Не добавляйте произвольные чужие домены. Ссылки приложение не открывает и не проверяет как банковские платежи; это защита от ошибочных/опасных URL, не проверка подлинности счёта.

## Telegram и почта
1. Напишите своему боту `/start` в личном чате. На сервере `npm run telegram:chat-id` показывает найденные Chat ID, не печатая токен. Помощник не отключает существующий webhook.
2. В админке задайте Chat ID и/или почту администратора, включите нужные каналы и сохраните при выключенном приёме.
3. Выполните «Тест Telegram» и «Тест почты». SMTP-успех означает приём сервером отправки, не гарантию попадания во входящие.
4. Проверьте готовность документов, CAPTCHA и включите приём. На сайте не нужно раскрывать токен или SMTP-секреты.
5. Выполните собственную тестовую заявку: база/админка → нужные каналы → заметка → счёт → ручная сверка/закрытие.

## Защита от спама и параллельных заявок
- Серверный подписанный HttpOnly/SameSite=Strict cookie браузера; Secure в production, срок 7 дней.
- Одна активная заявка на нормализованный телефон ИЛИ browser-cookie. Российские `8…`, `+7…` и десятизначный локальный формат приводятся к одному виду.
- Телефон/браузер заблокированы, пока заявка не завершена/отменена. После создания также действует интервал 10 минут; смена статуса не обходится мгновенной повторной заявкой.
- Проверка и вставка блокировок/заявки выполняются в одной транзакции. Проверено соперничество независимых процессов на одной SQLite.
- Постоянные лимиты в БД: 3 новых попытки на телефон/браузер за 10 минут, 20 попыток с IP за 10 минут, 60 новых попыток суммарно в минуту. Невалидные попытки также могут расходовать лимит.
- До разбора JSON действует дешёвый ограничитель API в памяти; заявка ограничена 20 KB, общий API — 3.2 MB. Дополнительные edge-лимиты есть в Nginx-шаблоне.
- `X-Real-IP` доверяется только от явно указанных адресов вашего reverse proxy; произвольный XFF не используется. Порт Bun закрывается от внешнего доступа.
- CAPTCHA Turnstile с серверной проверкой hostname/action и отказом при ошибке. По умолчанию в production-примере обязательна; отсутствие ключей выключает приём. Не использованы тестовые ключи в release. Перед включением проверьте доступность выбранного сервиса для аудитории РФ и его условия обработки данных; при необходимости замените провайдера до запуска.

Это не доказательство личности. Один человек с новыми телефоном, cookie и IP может выглядеть как другой; SMS-верификации нет. Телефон может принадлежать другому человеку. Абсолютной защиты от распределённого DDoS код приложения не даёт: нужны анти-DDoS у хостера/CDN, закрытый origin, WAF, TLS и наблюдение. На рабочий домен нагрузка не отправлялась.

## Очередь и эксплуатация
Заявка быстро сохраняется, HTTP не ждёт Telegram/SMTP. Постоянный Bun-процесс подбирает очередь каждые 15 секунд. Каналы независимы, до 5 попыток с увеличивающейся задержкой. Зависшая попытка восстанавливается через 2 минуты; ручной повтор доступен в админке. Несколько воркеров захватывают запись условным SQL-update, а поздний результат старой попытки защищён проверкой номера попытки.

После сетевого таймаута внешняя доставка может быть неизвестна: дубль уведомления при повторе остаётся возможным. Бизнес-заявка с тем же `requestId` не дублируется. Уведомления, уже помеченные отправленными, повторно не отправляются. Worker требует постоянно работающий процесс; на serverless-хостинге ему нужен отдельный планировщик/worker.

`/api/health` — процесс; `/api/ready` — доступность схемы БД. Настройте внешний мониторинг этих адресов и ошибок журнала, регулярно проверяйте очередь в админке. Автоматическое внешнее аварийное оповещение без данных провайдера не подключено.

HMAC-ключи IP/телефона/браузера — псевдонимизация, не юридическое обезличивание. Старые лимиты очищаются воркером после суток, неактивные блокировки — после закрытия/удаления заявки и истечения периода. Сроки хранения самих заказов и резервных копий определяет оператор. Согласие сохраняется вместе с текстом текущей политики и её хешем.

## Резервные копии
`npm run db:backup` делает локальный SQLite snapshot через VACUUM INTO, не небезопасное копирование живого db-файла. Каталог 0700, файл 0600. Он содержит персональные данные. Для удалённой Turso/libSQL используйте штатные snapshots провайдера: этот helper намеренно отказывается от remote URL.

До восстановления остановите приложение, восстановите snapshot в отдельный файл, проверьте `PRAGMA quick_check`, затем переключите `DATABASE_URL` и проверьте приложение. Автоматическое расписание и вынос за пределы сервера настраивает владелец инфраструктуры.

## Тесты
Скопируйте `.env.template` в `.env.orders-test.local`, задайте отдельную `DATABASE_URL=file:./orders-v2-test.db`, временные секрет и администратора, `WEBSITE_URL=http://localhost:4200`, `ORDER_CAPTCHA_REQUIRED=false`, `NOTIFICATION_WORKER_ENABLED=false`.

Из `packages/web`, используя системный Bun:
```sh
bun --env-file=../../.env.orders-test.local x drizzle-kit push
bun --env-file=../../.env.orders-test.local tools/seed.ts
bun --env-file=../../.env.orders-test.local tools/setup-orders.ts
bun --env-file=../../.env.orders-test.local tools/test-orders.ts
bun --env-file=../../.env.orders-test.local tools/test-upgrade.ts
```
Для повторного прогона очистите только выделенную тестовую БД. Тесты создают фиктивные заявки/статусы и меняют настройки — не запускайте на рабочей БД. SMTP проверяется на локальном тестовом сервере, Telegram и CAPTCHA имитируются. Результаты приёмки — `TEST-RESULTS-V2.md`.
